# StarSkill Agent 评测设计

日期：2026-07-20  
状态：待用户审阅

## 1. 目标与范围

本设计将 StarSkill 定义为一个面向 AI Agent 的天文实训 Skills 包。产品入口仍是 `run-starskill`，底层复用现有 `starskill` CLI。评测工作的重点不是增加更多天文功能，而是证明明确的天文任务能够形成稳定、可检查、可复现的闭环。

本阶段交付范围包括：

- 三类天文工作者 Agent 的独立评测；
- 固定基准任务、参数变体、失败集和开放压力任务；
- 机器可验证的产物检查和量化评分；
- 一轮轮换式交叉复核；
- 评测记录、失败原因和重复运行稳定性报告；
- 老旧工具接口标准化、运行加速和可复现重构的证据化加分机制。

本阶段不包括：

- Web 前端或独立桌面界面；
- 仓库内部直接调用 LLM API 或自动创建 Agent；
- 望远镜控制、实时天气保证、场地安全判断；
- 占星、命理或无来源科学结论；
- PPT/PDF 展示材料制作。

## 2. 已确认的设计决策

### 2.1 产品形态

产品第一身份是可被 Agent 调用的 Skills 包，而不是普通天文聊天助手。六类能力保留为内部清晰的职责边界：

1. 目标解析；
2. 星历计算；
3. 观测规划；
4. 公开数据获取；
5. 可视化生成；
6. 运行记录与人工复核。

对 Agent 暴露一个工作流入口，避免为同一套 CLI 维护多份重复的 `SKILL.md`。`run-starskill` 负责工作流选择、调用顺序、退出码处理、产物检查和安全边界；Python 模块负责实际计算和数据处理。

### 2.2 评测角色

第一阶段固定三类角色：

- 课程教师：生成 M42 观测计划，关注课堂可执行性、安全和人工复核；
- 科普讲解员：生成上海月亮—木星位置关系材料，关注科学表达和公众可理解性；
- 科研入门指导者：生成 M51 SDSS 公开图像展示材料，关注来源、处理记录和可复现性。

三类角色先独立运行，所有运行完成后再执行交叉复核，防止角色之间通过共享上下文掩盖问题。

### 2.3 Agent 调度边界

Codex 评测会话负责创建独立 Agent。仓库只提供 provider-neutral 的案例、角色提示词、产物契约、检查器、评分器和报告模板，不绑定模型供应商、API 密钥或特定的子 Agent 调度接口。

这样既可以在 Codex 中使用子 Agent，也可以把已保存的 Agent 输出重放给离线评分器，保证 Skills 本身不被评测平台实现细节绑死。

## 3. 评测架构

评测链路如下：

```text
case.json
    |
    +--> 课程教师 Agent --------+
    +--> 科普讲解员 Agent ------+--> 独立产物目录
    +--> 科研指导者 Agent ------+
                                      |
                                      v
                             机器硬门槛与事实检查
                                      |
                                      v
                             轮换式交叉复核 Agent
                                      |
                                      v
                            分数聚合、稳定性与报告
```

每个 Worker Agent 使用全新上下文、独立输出目录和同一版本的角色提示词。Worker 不能读取其他 Worker 的运行记录，也不能读取复核意见。

建议的评测目录结构为：

```text
evaluation/
  cases/
    core/
    variants/
    failures/
    open/
  prompts/
    workers/
    reviewers/
  checks/
  scoring/
  reports/
  README.md

evaluation-runs/
  case-001-m42-beijing/
    case.json
    workers/
      teacher-run-01/
        response.md
        tool_calls.jsonl
        artifacts/
        machine_checks.json
    reviews/
      reviewer-1.json
    score.json
```

`evaluation/` 保存可复用的评测定义和评分逻辑；`evaluation-runs/` 保存具体运行记录，原始回答和产物不可被后续评分覆盖。

## 4. 标准数据流

### 4.1 案例定义

每个 `case.json` 至少声明：

- `case_id`、角色和任务类型；
- 输入 JSON 或输入生成规则；
- 允许使用的 CLI/Skill 工作流；
- 必需产物及相对路径；
- JSON/CSV Schema 和字段检查；
- 数值参考值与允许容差；
- 允许的成功、降级和失败状态；
- 角色复核重点；
- 是否属于核心、变体、失败或开放任务。

评分器只信任案例定义和实际文件，不信任 Worker 自己声称的分数或成功状态。

### 4.2 Worker 执行

Worker Agent 接收角色上下文、案例任务和 `run-starskill` 使用说明，在自己的目录中调用 CLI。它必须保存：

- 面向用户的最终回答；
- 每次 Skill/CLI 调用及参数；
- 标准输出、标准错误和退出码；
- `run.json` 等工作流产物；
- 对图片、数据源和人工复核项的说明。

Worker 不得用文字替代实际文件，不得在外部服务失败时补写伪造坐标、图像、来源或成功报告。

### 4.3 机器检查

机器检查负责确定性强的事实：

- 命令是否实际执行以及退出码是否符合契约；
- 报告声称的文件是否存在、非空且路径正确；
- JSON/CSV 是否符合 Schema、字段类型和单位约定；
- 天文数值是否落在案例定义的参考容差内；
- 来源、访问时间、缓存状态和依赖版本是否被记录；
- `run.json` 中登记的字节数和 SHA-256 是否匹配；
- 图片的格式、尺寸、非空像素和元数据是否有效；
- 失败或降级时是否没有留下假成功产物。

机器检查拥有文件、Schema、数值、哈希和退出码事实的最终裁决权。

### 4.4 交叉复核

所有独立 Worker 完成后，才启动复核 Agent。复核 Agent 只能读取案例、被复核回答、产物和机器检查结果，不读取其他复核 Agent 的意见。

复核采用轮换方式：教师复核科普输出，科普讲解员复核科研输出，科研指导者复核教师输出。复核重点是角色可用性、解释准确性、人工复核边界和开放任务中的能力边界，不重复替代机器数值检查。

复核结果统一写成结构化 JSON，包含复核角色、维度分数、问题列表、严重级别、置信度和建议。若复核 Agent 标记严重问题，或机器检查与复核结论冲突，才触发一次独立仲裁；普通任务不进行多轮辩论。

## 5. 评测任务矩阵

### 5.1 固定基准

固定基准包含仓库现有三个真实案例：

1. 北京 M42 观测计划：验证目标解析、星历、可观测窗口、曲线、报告和安全复核；
2. 上海月亮—木星关系：验证多目标天象计算、角距离解释、位置表和科普边界；
3. M51 SDSS 图像展示：验证公开数据请求、缓存、响应校验、图像处理、元数据和来源。

这三个案例是主要闭环验收依据。

### 5.2 参数变体

每个固定案例定义两个变体，共 6 个：

- M42：修改目标/城市/日期/观测时段或观测阈值；
- 月亮—木星：修改城市、日期、时间范围或采样间隔，但仍遵守只支持 Moon 与 Jupiter 的输入契约；
- M51：修改当前 Schema 支持的坐标、尺寸、比例尺、超时、大小限制或缓存参数，不虚构任意星系下载能力。

变体用于验证流程可复用，而不是要求 Skills 支持题目之外的接口。

### 5.3 失败集

第一版失败集覆盖以下明确场景：

- 缺少必需字段或存在额外字段；
- 经纬度、时区、时间范围或阈值非法；
- 目标名称非法、目标不存在或 SIMBAD 服务失败；
- 全晚没有合格观测窗口；
- SDSS 无数据或服务失败；
- SDSS 响应超出大小限制、不是 JPEG 或尺寸不匹配。

失败集的期望结果不是“成功”，而是正确退出码、结构化错误、可解释的降级状态和无假产物。

### 5.4 开放压力集

每类角色各设置一个开放任务，共 3 个。开放任务可以要求 Agent 组合已有能力、改变输入条件或处理超出当前契约的请求。它不改变核心通过门槛，但单独输出量化泛化分、失败模式和改进建议。

开放任务必须仍处于天文实训范围内；遇到不支持的目标、数据源或安全判断时，正确识别边界比强行生成结果更高分。

## 6. 硬门槛与评分

### 6.1 硬门槛

以下任一情况直接标记任务为 `fail`，额外加分不能抵消：

- 未实际调用对应 Skill，或伪造坐标、图像、来源或成功状态；
- 关键产物缺失、损坏，或报告声称存在但文件不存在；
- 外部服务失败时没有进入明确的失败/降级状态；
- 把候选观测窗口说成天气、设备或安全保证；
- 把月亮—木星的天球角距说成真实空间距离；
- 删除或跳过题目要求的人工安全复核。

### 6.2 基础分

通过硬门槛后，基础分为 100 分：

| 维度 | 分值 | 评分重点 |
|---|---:|---|
| 闭环完成度 | 40 | 输入校验、工作流调用、中间结果、最终材料、复核入口和参数变体复用 |
| 科学正确性 | 25 | 目标、坐标、时间、单位、数值容差、科学概念和数据来源 |
| 可复现性 | 20 | 输入、依赖、查询参数、缓存、访问时间、产物哈希和重复运行 |
| 错误处理与安全 | 10 | 无效输入、网络失败、无数据、图表降级和人工确认边界 |
| 角色可用性 | 5 | 是否符合教师、科普讲解员或科研指导者的工作目标 |

评分结果必须保存每项得分、证据路径、扣分原因、复核意见和未覆盖风险，不能只保存总分。

### 6.3 额外加分

额外加分最多 10 分，且不影响硬门槛：

- 老旧但常用天文工具的接口标准化：最多 3 分；
- 有基线数据证明的运行加速：最多 3 分；
- 有测试、输入输出契约和运行记录证明的可复现重构：最多 4 分。

所有额外加分必须提交前后对比、测试结果或运行记录作为证据，不能因为增加代码量直接获得加分。

开放压力任务另按 20 分记录：工作流选择、边界识别、产物闭环和说明质量各 5 分。开放分不计入核心基础分，只用于泛化能力报告。

## 7. 重复运行与通过线

为了区分 Skills 能力和单次模型随机性，固定三个基准案例各由 3 个独立 Worker Agent 实例运行，共 9 次。每次使用全新上下文和独立目录。

参数变体、失败集和开放压力集第一版各运行 1 次；若发现基础设施错误或结果出现严重分歧，可做诊断重跑，但不得静默覆盖原始结果。

每次运行记录模型标识、角色提示词版本、代码版本、缓存冷热状态、网络模式、工具调用、退出码、耗时和所有评分结果。

第一版通过线为：

- 固定基准的 9 次运行全部通过硬门槛；
- 6 个参数变体的硬门槛通过率至少 90%，按当前样本量实际要求为 6/6；
- 核心任务平均基础分至少 80 分；
- 每个固定案例的三次重复运行分数标准差不超过 5 分；
- 不出现伪造数据、来源、成功状态或安全保证。

核心验收使用经过校验的真实缓存或响应快照，避免公共服务波动污染评分。另设 live smoke test 检查 SIMBAD 和 SDSS 当前服务健康度，但 live 结果不直接决定 Skills 是否合格。

## 8. 失败处理与边界

评测系统必须区分以下状态：

- Worker 未启动、评测器崩溃或复核 Agent 超时：评测基础设施失败，保留记录并单独重跑；
- Skills 返回预期的结构化错误或降级结果：属于正确处理，按错误处理维度评分；
- Skills 返回错误成功状态、伪造产物或越过安全边界：属于硬门槛失败；
- 外部服务暂时不可用但已有合法缓存：允许使用并记录缓存命中；
- 外部服务不可用且无缓存：允许失败或降级，但不得伪造结果。

机器评分失败不应通过删除输入、覆盖原始产物或手工改写结果解决。所有重跑都使用新的运行目录，并在最终报告中区分原始运行和诊断运行。

## 9. 测试策略

评测层本身需要独立测试：

- 检查器单元测试：文件、Schema、哈希、CSV 字段、数值容差、图片属性和退出码边界；
- 评分器单元测试：硬门槛优先级、分数边界、标准差、加分上限和失败状态；
- 案例契约测试：三类固定案例的必需产物、允许状态和复核项完整；
- 网络/缓存集成测试：使用假的 SIMBAD/SDSS 后端覆盖成功、缓存、服务失败、超限和损坏缓存；
- 端到端重放测试：用保存的 Worker 输出重建机器检查、交叉复核输入和最终评分；
- live smoke test：单独运行真实公共服务，不纳入无网络 CI 的必过测试。

核心产品现有的 Python 测试继续负责天文计算和 CLI 行为；评测层不重复实现天文计算，而是验证 CLI 已声明的输入输出契约。

## 10. 交付与验收产物

完成后应有：

- `evaluation/` 案例、提示词、检查器、评分器和使用说明；
- 三类固定任务的真实运行目录；
- 参数变体和失败集的运行记录；
- 开放压力任务的单独评分报告；
- 每次运行的原始回答、工具调用、产物、机器检查、复核和最终分数；
- 一份汇总报告，分别列出闭环完成度、科学正确性、可复现性、安全边界、角色可用性、稳定性和额外加分证据。

最终报告必须把计算事实、规则判断和人工复核项分开描述，不能把“候选观测窗口”包装成现场观测保证，也不能把展示图的处理结果包装成未经处理的科学数据。

## 11. 主要风险与应对

| 风险 | 应对 |
|---|---|
| 模型随机性造成评分波动 | 固定角色提示词，独立重复运行，记录均值、中位数、最低分和标准差 |
| SIMBAD/SDSS 网络波动 | 核心评分使用校验快照，live smoke 单独报告 |
| 复核 Agent 被语言质量误导 | 数值、文件和来源由机器检查裁决，复核只补充角色和边界评价 |
| 评测要求超出当前 CLI 契约 | 案例只使用已声明支持的参数；开放任务允许诚实拒绝 |
| 额外功能堆叠但没有价值 | 加分必须有基线、测试、前后对比和可复现运行证据 |
| 评测平台绑定特定 Agent API | 由外部 Codex 会话负责调度，仓库保留 provider-neutral 重放协议 |

本设计的核心结论是：StarSkill 的竞争力来自可复现的任务闭环和可审计的 Agent 工具调用，而不是功能数量。评测层应优先证明这一点，再用标准化、加速和重构证据体现工程价值。
